# Recommended schema for separate tomato, potato, and banana simulations

## Decision

Keep the tomato, potato, and banana experiments separate from one another and
from the existing five-crop, 20,000-row simulation. Do not join source records
from different studies as though they came from one fruit, tuber, storage lot,
or time point.

The existing Edition 2 CSVs are a small binary-label demonstration. They have
600 independent generated cases per crop, not 600 inspected physical samples.
The labels are generated by a simulator rule. Keep those files and their
models as the old binary run; do not overwrite them when making a refined
version.

## Keep in each simulated observation table

Each row should represent one simulated sample at one observation time.
Column names with `_SIM` make synthetic content visible in the table itself.

| Column | Include? | Purpose |
|---|---|---|
| `sim_case_id` | Yes | Unique case key for the current one-time demo. |
| `sim_sample_id` | Yes if a sample has repeated times | Groups a simulated physical sample across readings; use for grouped splits. |
| `crop` | Yes | `tomato`, `potato`, or `banana`; separate files remain primary. |
| `crop_stage_SIM` | Yes | States the stage assumed by the scenario (e.g. mature-green tomato, table potato, mature-green banana). |
| `storage_scenario_SIM` | Yes, audit-only | Describes the generated condition path; never feed it to the model. |
| `storage_age_days_SIM` | Yes | Elapsed storage time at the observation, if the simulation includes age. |
| `temperature_C_SIM` | Yes | Simulated storage-air temperature. |
| `relative_humidity_pct_SIM` | Yes | Simulated relative humidity. |
| `MQ2_response_SIM` … `MQ135_response_SIM` | Yes | Nine channel responses, in a stated response scale; not gas ppm. |
| `quality_state_SIM` | Yes | `acceptable`, `warning`, or `high_risk`; generated by the documented simulator rule, not inspection. |
| `data_origin` | Yes | Fixed value such as `SIMULATED_RULE_BASED`. |
| `label_rule_version_SIM` | Yes | Identifies the exact rule that produced the simulated class. |
| `mq_source_recording_SIM` | Yes for source-resampled readings | Names the separate source recording used as a distribution reference. This is provenance only, not a predictor. |

For the current one-time version, `sim_case_id` is enough as the grouping key.
If the next version is longitudinal, use `sim_sample_id` for each fruit/tuber
and repeat it across observation times; then hold out whole sample IDs. A
single-time case cannot support a remaining-life target.

## Keep in metadata or inspection/outcome tables, not predictor columns

| Field | Why retain it |
|---|---|
| `simulation_seed`, `simulation_version`, source DOI, assumptions, channel scale | Reproducibility and provenance. A small README/JSON sidecar is fine for constant metadata. |
| Real `lot_id`, `sample_id`, `timestamp_utc`, `storage_age_days` | Required to prove same-sample/time matching and group validation when real measurements arrive. |
| `quality_state` and its inspection rubric, inspection time, inspector/assessor code | Ground truth must come from documented independent crop inspection. These are targets, not model inputs. |
| `defect_type`, visible decay/rot, firmness, sprouting/greening, weight loss or lab measures | Useful outcome detail only when actually inspected/measured; crop-specific and not interchangeable. |
| `failure_interval_start_days`, `failure_interval_end_days`, `event_observed`, `observed_followup_days` | Survival targets. For samples still acceptable at the end, record censoring rather than an invented failure day. |
| `sensor_device_id`, channel mapping, calibration/baseline version, warm-up and measurement-window details | Necessary to interpret and reproduce sensor responses; normally metadata, not predictive features. |

Do not put a simulator's internal deterioration score in the predictor table.
If retained for debugging, put it in a separate audit output and mark it as
forbidden for model inputs.

## Do not add

- Do not create `ppm` columns from MQ module voltages or ADC values. Keep raw
  output or a documented calibrated ratio such as `Rs/R0`; MQ sensors are
  cross-sensitive, and their response is affected by temperature and humidity.
- Do not make a real-data row look complete by inventing missing MQ channels,
  environmental readings, sample IDs, inspections, or survival outcomes.
- Do not use storage scenario, IDs, absolute fictional dates, inspection
  outcomes, simulator scores, or future readings as predictors.
- Do not add pressure, altitude, dew point, heat index, light, or other derived
  fields to this small crop simulation unless they are measured or specifically
  required. Preserve real device-exported columns in a raw archive; compare
  derived/redundant inputs separately during model evaluation.
- Do not label banana ripening (`green`, `ripe`) as spoilage. Ripeness and
  spoilage are different targets. Tomato color/ripeness and potato storage day
  are also not automatically an inspected spoilage label.
- Do not concatenate tomato, potato, banana, AeroSense, and nine-MQ source
  files without verified physical sample and time keys.

## Feature sets

Keep separate, reproducible feature lists for each crop:

1. Environment-only: `temperature_C_SIM`, `relative_humidity_pct_SIM`, and
   age only if the prediction time makes it available.
2. MQ-only: the nine channel response fields.
3. Combined: both groups.

Exclude identifiers, scenarios, data-source fields, labels, inspection
measurements, simulator internals, and future values. Any historical feature
must be calculated from readings at or before the prediction time.

## What the source files actually support

- **Tomato Zenodo 15469472:** sample ID, storage scenario/day, weight, color,
  and 12 sensor-response fields (`Rs/R0`-based); its rows do not supply a
  verified `acceptable/warning/spoiled` inspection target or matched AeroSense
  temperature/RH. [Dataset](https://zenodo.org/records/15469472)
- **Nine-MQ Zenodo 17285312:** the requested nine MQ channels in short
  approximately three-minute recordings, taken at daily intervals around room
  temperature; it does not provide matched environmental paths and
  independent inspection labels. Do not treat D1–D5 as verified spoilage
  classes. [Dataset](https://zenodo.org/records/17285312)
- **Potato storage Mendeley archive:** environmental histories and separate
  quality summaries; no MQ readings or verified per-sample sensor-to-quality
  join. Potato e-nose papers show useful measurement designs, but their
  published storage-period or chemistry targets are not automatically
  spoilage labels. [Archive](https://data.mendeley.com/datasets/sbwxmtpj47/1)
- **Banana:** the nine-MQ recordings above include banana files; separate
  banana environmental/VOC sources are not the same physical samples. Do not
  join them.

## Research-guided scenario ranges, not class thresholds

Use these sources only to choose plausible simulated storage scenarios. They
do not define the simulated quality labels, and recommendations depend on crop
stage, cultivar, and intended use.

- [UC Davis tomato guidance](https://postharvest.ucdavis.edu/produce-facts-sheets/tomato): tomato temperature depends on maturity stage; the source notes 90–95% RH and chilling/decay risks at particular temperatures and durations.
- [UC Davis potato guidance](https://postharvest.ucdavis.edu/produce-facts-sheets/potato): early/table potato handling and storage recommendations differ by intended use and maturity.
- [UC Davis banana guidance](https://postharvest.ucdavis.edu/es/produce-facts-sheets/banano-platano): storage recommendations differ from consumer-ripening conditions; below-recommended temperatures can cause chilling injury.
- [Winsen MQ-4 datasheet](https://www.mouser.com/datasheet/2/813/MQ-4_Ver1.3_-_Manual-1509240.pdf): defines `Rs/R0` with `R0` measured in clean air and includes temperature/humidity response characteristics. This supports keeping channel scale and calibration explicit, not treating the sensor output as an exact gas concentration.

## Next implementation

Create a new `simulated_v3` folder per crop using this schema. Use three
simulator-only states and retain the label rule in metadata. Train and evaluate
separate crop models with grouped splits if repeated simulated samples are
included. Keep v2 files/models unchanged. When real paired, inspected records
arrive, preserve their raw measurements, replace synthetic target labels with
inspection outcomes, train on real training lots, and evaluate only on
untouched real lots. Compare real-only versus real-plus-simulation training;
keep simulated training data only if it improves the held-out real-lot result.
